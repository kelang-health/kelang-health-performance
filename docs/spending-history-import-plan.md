ตรวจเมื่อ 19 ตุลาคม 2569 เพื่อเตรียมพัฒนา ไม่ใช่การรับรองยอดปิดปี ผลติดตั้งภายหลังอยู่ท้ายเอกสาร

## ข้อสรุป

ใช้โครงสร้าง 8 หน่วยและ 11 หมวดเดิมเป็นฐานได้ มีข้อมูลจ่ายตั้งต้นของปี 2567 และ 2568 แต่ต้องนำเข้าเป็นร่างที่หน่วยตรวจสอบ พร้อมวันตัดยอดและแหล่งที่มา ไม่เผยแพร่เป็นยอดจ่ายจริงครบปีโดยอัตโนมัติ

## รูปแบบระบบที่จะทำ

1. เพิ่มส่วน “ประวัติรายจ่าย” ในหน้าการใช้เงิน เลือกปี หน่วย และวันที่ข้อมูลครอบคลุมได้ ปีเริ่มต้น 2568–2569 และรองรับปี 2567 จากไฟล์ที่ส่งเพิ่ม
2. ตารางประวัติแยกจากรายงานติดตามแผนปี 2570 เก็บหนึ่งชุดต่อหน่วย/ปี พร้อมหมวด รายการย่อย ช่วงเวลา แหล่งที่มา สถานะ revision และข้อสังเกต รองรับเพิ่มข้อมูลรายเดือนภายหลังเมื่อมีหลักฐาน โดยไม่แบ่งยอดสะสมย้อนหลังเป็นเดือนเอง
3. ช่องแก้ไขหลักคือจ่ายจริงที่ยืนยันช่วงเวลาแล้ว วงเงินแผนและงบผูกพันเป็นคนละช่อง ยอดรวมคำนวณอัตโนมัติและไม่นับหัวข้อซ้ำกับรายการย่อย
4. รายการนำเข้าแสดง “ข้อมูลตั้งต้น รอตรวจสอบ” พร้อมที่มา กรอกร่างแม้ไม่ครบได้ ยืนยันแยกระดับหมวดพร้อมช่วงเวลาที่ครอบคลุม หน่วยที่ยอดขัดกันเห็นทั้งสองค่าและระบุเหตุผลเมื่อเลือกหรือแก้ยอด
5. STAFF แก้เฉพาะหน่วยตนเอง MONITOR ดูทุกหน่วยและแก้เฉพาะหน่วยที่ได้รับมอบหมาย ADMIN จัดการทุกหน่วยและเปิดแก้ข้อมูลที่ยืนยันแล้วพร้อมเหตุผล ใช้ประวัติการแก้ไขและป้องกันบันทึกทับ revision เดิม
6. ผู้บริหารเลือกหน่วยเดียวดูทุกหมวด หรือหมวดเดียวดูทั้ง 8 หน่วย แสดงยอดสองปี ส่วนต่างบาท ร้อยละ และความครบถ้วน เทียบได้เฉพาะช่วงเวลาและหมวดที่ตรวจสอบแล้วตรงกัน ฐานศูนย์แสดง “เริ่มมีรายจ่าย” ฐานหายแสดง “ยังเปรียบเทียบไม่ได้” ไม่ใช้สีเพิ่ม/ลดสื่อว่าดี/เสียโดยอัตโนมัติ
7. ยอดรายเดือนปี 2569 ที่มีในระบบใช้เป็นยอดควบคุมแยกต่างหาก ตรวจส่วนต่างกับรายหมวดเฉพาะช่วงเวลาเดียวกัน ไม่บวกข้อมูลนำเข้าเพิ่มกับยอดเดิมซ้ำ ไม่สร้างรายการรายเดือนจากยอดสะสม
8. ข้อมูลปี 2569 จากไฟล์ที่ส่งก่อนหน้านี้ต้องคงจ่ายจริงถึงสิงหาคมกับงบผูกพันกันยายนแยกกันก่อน ยอดผูกพันจะเป็นจ่ายจริงได้เมื่อหน่วยยืนยันการจ่าย

## ลำดับงานและเกณฑ์ทดสอบ

1. สร้างโครงสร้างและสิทธิ์ตามขอบเขตหน่วย พร้อมแบบฟอร์มแก้ไข/ยืนยันและ audit
2. นำข้อมูลเข้าเป็นร่าง: ปี 2568 จากไฟล์นำเสนอ ปี 2567 จากไฟล์ตรงปี และปี 2569 จากแหล่งเดิม เก็บฉบับแผนเป็นหลักฐานแยกจากจ่ายจริง
3. ให้หน่วยยืนยันวันตัดยอด ศูนย์ที่ยังไม่ทราบ และส่วนต่างบ้านฟ่อน/เขลางค์นคร ตรวจหมวดที่เปลี่ยนความหมายก่อนเปิดเปรียบเทียบ
4. ทดสอบการระบุปีจากเนื้อหา รหัสนำหน้า 0 คอลัมน์ร้อยละแยกจากบาท สูตรรวมช่องว่าง การรวมหมวดโดยไม่ซ้ำ การนำเข้าซ้ำไม่สร้างยอดซ้ำ และการเก็บรายการย่อยครบ
5. ทดสอบ STAFF/MONITOR ข้ามหน่วยต้องเขียนไม่ได้ ADMIN เปิดแก้ต้องมีเหตุผล ยืนยันแล้วล็อกตามขั้นตอน และป้องกันการแก้พร้อมกัน
6. ทดสอบช่วงเวลาไม่เท่ากันต้องไม่คำนวณแนวโน้ม ฐานศูนย์/ข้อมูลขาดไม่เกิดหารศูนย์ เปรียบเทียบใช้เฉพาะข้อมูลที่ยืนยันและครอบคลุมช่วงเดียวกัน
7. เมื่อพัฒนาและตรวจข้อมูลผ่านจึงอัปเดตรุ่น ทดสอบ build และเผยแพร่เว็บ ไม่เปลี่ยนยอดเว็บจริงระหว่างขั้นตรวจแหล่งข้อมูลนี้

## ผลติดตั้งรุ่น 1.89

- เพิ่มหน้า `#spending-history` สองแท็บ: ภาพรวมและเปรียบเทียบ / ตรวจสอบและแก้ข้อมูลย้อนหลัง ตัวกรองแยกจาก `#spending` และปีหลักของเว็บ
- เพิ่มตารางเดียว `hp_spending_history` พร้อม RLS ใช้ helper สิทธิ์และ session เดิม เก็บหลักฐานต้นฉบับแบบแก้ไม่ได้ ควบคุม revision และ audit ด้วย `hp_audit_logs` เดิม ไม่ให้ลบข้อมูลประวัติโดยตรง
- นำข้อมูลเข้าเป็นร่าง 24 ชุด 8 หน่วย × ปี 2567,2568,2569 รวม 264 หมวด พร้อมรายการย่อยและข้อสังเกต เก็บปี 2569 เป็นจ่ายจริงถึงสิงหาคมและผูกพันแยกต่างหาก ปี 2567–2568 ไม่กำหนดวันตัดยอดแทนเจ้าหน้าที่
- เมื่อลงรายละเอียดครบ ระบบรวมยอดหมวดอัตโนมัติ รองรับกรอกยอดหมวดตามหลักฐานรวมโดยต้องอธิบายหากรายละเอียดไม่ครบ/ยอดต่างกัน
- การยืนยันต้องครบ 11 หมวด มีช่วงเวลาภายในปี และบันทึกผลตรวจข้อสังเกต ล็อกหลังยืนยัน ADMIN เปิดแก้โดยให้เหตุผลก่อน
- เปรียบเทียบเฉพาะยอดยืนยันที่วันเริ่ม–สิ้นสุดตรงช่วงเดียวกันข้ามปี ช่องว่างไม่เป็นศูนย์ และผูกพันไม่รวมเป็นจ่ายจริง
- ตรวจ checksum ของ `hp_spending_reports`, `hp_budget_monthly`, `hp_finance_monthly` ปี 2570 ก่อน–หลังตรงกัน ไม่มีการเปลี่ยนยอดหรือแผนปี 2570 จากงานนี้
- SQL ทดสอบสิทธิ์และข้อมูลบน Cloud ใน transaction แล้ว rollback ผ่าน STAFF/MONITOR/ADMIN/อ่านอย่างเดียว/ไม่มีสิทธิ์/anon, source immutable, revision, ช่วงเวลา, จำนวนเงิน, ล็อกยืนยันและ audit
- ทดสอบ UI จำลอง REST: บันทึกร่าง ยืนยัน เปิดแก้ สิทธิ์ทุกบทบาท เปรียบเทียบช่วงเดียวกัน ตัวเลขผิด แจ้งข้อมูลยังไม่บันทึก รวมรายละเอียดอัตโนมัติ 390/768/1440px และสลับหน้า 2570 โดยตัวกรองเดิมยังอยู่ ผ่านทั้งหมด ไม่สร้างยอดทดสอบจริง
- Unit tests รวม 175 tests และ build ผ่าน ตรวจ security advisors แล้วไม่มีรายการใหม่เกี่ยวกับตาราง/ฟังก์ชันนี้ รายการเดิมของ `hp_touch_session` เป็น endpoint สำหรับผู้เข้าสู่ระบบตามการออกแบบ ([คำอธิบาย advisor](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable))
- ไฟล์นำเข้าและต้นทางอยู่ใน `backups/` ที่ถูก exclude จาก Git และ public build ไฟล์บนเว็บไม่บรรจุข้อมูลย้อนหลังแบบสาธารณะ อ่านผ่านฐานข้อมูลตามสิทธิ์เท่านั้น
